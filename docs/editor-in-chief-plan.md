## Approach

### 1. Establish the public project and a small executable host
Create a Bun/TypeScript application, using `bun:sqlite` for local operational state, `node:util.parseArgs` for the CLI, Zod for validating external/model data, and dotenv solely to parse the designated credential file without executing it. Pin `@oh-my-pi/pi-coding-agent` to `18.2.7`; commit the resolved Bun lockfile. There is no existing implementation in this repository to extend. Do not add a server, web dashboard, job framework, or a second agent runtime.

New source ownership:
- `src/cli.ts`, `src/config.ts`, `src/state.ts`: commands, validated configuration, checkpoint/state storage.
- `src/sources/github.ts`, `bluesky.ts`, `hindsight.ts`: fixed read-only collection adapters.
- `src/editor.ts`, `src/contracts.ts`, `prompts/editor-in-chief.md`: restricted OMP persona, structured requests/results, editorial policy.
- `src/workspace.ts`, `src/metrics.ts`, `src/run.ts`: bounded GitHub writes, outcome collection, orchestration.

Expose `bun run eic` through package scripts, with these verbs:
- `doctor`: read-only prerequisite/API/model checks and sanitized capability report; no GitHub mutations or paid model prompt.
- `bootstrap --apply`: idempotently create labels, the editorial project, inbox, and prerequisite issues in the already-created repository.
- `run --dry-run` and `run --apply`: same collection/judgment path; dry-run persists only to the selected local state directory and prints proposed changes, never writes GitHub or records writes as delivered. Require an explicit mode.
- `review --pr <number> --dry-run|--apply`: exercise one eligible content PR immediately without waiting for cron.
- `record-publication --issue <number> --channel <channel> --url <https-url> --published-at <ISO-date-time> --kind original|derivative`: register a human publication and mirror its record in the story's managed issue section.
- `import-metrics <json-file>`: validate and ingest operator-supplied channel metrics.
- `status`: show last run, per-source coverage, backlog, active story, pending reviews, and metric availability without a model call.
- `schedule install`, `schedule show`, `schedule remove`: manage only the marked editorial crontab block; installation is an explicit operator action after smoke verification.

Shared flags: `--config <path>`, `--state-dir <path>`. Default public config is `editorial.config.json`; default state is `${XDG_STATE_HOME:-~/.local/state}/editor-in-chief/`, directory mode 0700, files 0600. Ignore local state, dotenv files, media, and generated run artifacts in git. Keep secrets out of config. Include only non-secret runtime/source identity and cadence in public config:
`githubOwner: "pedropaulovc"`, `repository: "pedropaulovc/editor-in-chief"`, `blueskyHandle: "pedro.vza.net"`, `hindsightUrl: "https://hindsight.vza.net"`, `hindsightEnvFile: "~/.omp/agent/.env"`, `timezone: "America/Los_Angeles"`, `cadence: "weekly"`, `model: "openai-codex/gpt-5.6"`, `thinking: "medium"`. Initialize `main`, copy this approved plan to `docs/editor-in-chief-plan.md`, and create `pedropaulovc/editor-in-chief` with public visibility. Preserve the canonical session-local plan rather than renaming it. Push the initial working implementation early and subsequent verified changes to `origin/main`. Do not commit source memory dumps or credentials.

### 2. Run a genuinely restricted custom OMP editor
Use SDK imports from the pinned package, reusing `createAgentSession`, `discoverAuthStorage`, `Settings.isolated`, and `SessionManager.inMemory`. Share the existing OMP credential store via `discoverAuthStorage("/home/pedro/.omp/agent")`; do not duplicate or manually refresh OAuth grants. Put editor runtime artifacts under the application state directory. No credential needs to appear in a model message.

Create a fresh session for each editorial request with:
- `systemPrompt: [personaText]`, not an appended coding-agent prompt;
- `settings: Settings.isolated({"memory.backend":"off", "autolearn.enabled":false})`;
- `contextFiles: []`, `skills: []`, `rules: []`, `promptTemplates: []`, `slashCommands: []`;
- `disableExtensionDiscovery: true`, `enableMCP: false`, `enableLsp: false`, `hasUI: false`;
- `toolNames: []`, `restrictToolNames: true`, `customTools: []`;
- explicit `modelPattern`, `thinkingLevel`, `sessionManager: SessionManager.inMemory()`, and a five-minute request deadline.

Before prompting, assert both `session.getActiveToolNames()` and `session.getEnabledToolNames()` are empty. If not, fail closed. This is important: CLI `--tools` alone is not the SDK's hard allowlist. Do not fall back to an unrestricted CLI or task subagent. The custom agent is the editorial persona executed by OMP, not a misleading `.omp/agents` file that cron cannot run directly.

Prefetch bounded, redacted evidence in host code; send it as clearly delimited untrusted data. Use `session.prompt`, inspect the terminal assistant state, parse `session.getLastAssistantText()` as one JSON result, validate it with Zod, and dispose in `finally`. Error/aborted/incomplete/invalid output must not reach the GitHub writer. Allow one schema-repair request with validation errors, then record a failure and retry at the next scheduled opportunity. Record actual model identity and available usage counts, not guessed dollar costs.

Use three explicit request/result kinds in `src/contracts.ts`: `triage`, `desk`, and `review`. Triage returns candidate source IDs, topic labels, reader questions, missing evidence, and links to an existing candidate when it is the same story. Desk returns at most three existing candidate IDs with briefs and at most one recommendation at weekly cadence. Review returns `headSha`, `verdict: "needs-work" | "ready"`, and located findings. Reject unrecognized fields, unprovided source IDs, nonexistent candidate IDs, and results for the wrong head. The model does not return arbitrary API requests, URLs to fetch, shell commands, or file mutations.

Transactions must not span network or model calls.

**GitHub.** Use authenticated `gh api` with argument arrays, never shell-interpolated strings. Enumerate public repositories and the user's contribution repositories using GraphQL `user(login:...).contributionsCollection(from:...,to:...)`; supplement with paginated authored PRs/issues, reviewed PRs, and recent public events. Events are a freshness hint, not the complete ledger: their history is capped. Fetch actual PR/commit/issue evidence rather than narrating activity totals. For contributed/priority repos, list commits over the checkpoint window; for Harmonic Analyzer include main-branch logbook and campaign changes even when the git author is an agent. Exclude this editorial repo's automation from story discovery while still reading its human capture/draft/workspace input, preventing self-generated issue feedback loops.

Bootstrap with the most recent 30 days, then use a 48-hour overlap on completed time windows. Follow REST `Link` and GraphQL `pageInfo` pagination. Partition search time windows when approaching GitHub's 1,000-result search ceiling. Bound work per run and persist unfinished windows; report partial coverage instead of advancing a checkpoint over skipped data. Keep older candidate history, and include a weekly 90-day lookback over contribution evidence for forgotten work. No crawler over every file of every project.

**Bluesky.** Call `https://public.api.bsky.app/xrpc/com.atproto.identity.resolveHandle`, `app.bsky.actor.getProfile`, and `app.bsky.feed.getAuthorFeed` with `actor=<DID>`, `limit=100`, `filter=posts_with_replies`, `includePins=false`. ### 4. Maintain a public editorial workspace that does not become another backlog
`bootstrap --apply` creates a public user Project V2 titled `Editor-in-chief`, links the new repository, and stores its actual node/field IDs locally. On state recovery discover by repository linkage plus exact title; if multiple matches exist, refuse to write and report their URLs rather than picking one. Use GraphQL project mutations and paginated reads; project access is already available.

The Project `Status` field is the human-facing source of truth: `Inbox`, `Selected`, `Drafting`, `Review`, `Ready`, `Published`, `Parked`. Pedro selects/parks a story by moving it. Host-observed draft and review/publication events advance later states; they must never unpark a story or override a newer manual selection. Set `Published` only with a registered publication record, not a board drag or merged PR. A bare move to Published generates one request for the missing URL/date and retains the prior verified status. Use labels `editorial-story`, `editorial-draft`, `editorial-capture`, `editorial-desk`, `editorial-prerequisite`, plus pillar labels `pillar:harmonic-analyzer`, `pillar:ai-engineering`, `pillar:side-projects`.

State mapping: a new story enters `Inbox`; an eligible linked PR sets `Drafting`; a submitted `needs-work` review sets `Review`; a `ready` review at the current head sets `Ready`; a subsequent unreviewed head returns it to `Drafting`; a registered original publication sets `Published`. `Selected` and `Parked` are Pedro-only transitions. Published stories stay Published when later derivatives are reviewed. Before an automatic transition, re-read the field and cancel the transition if its value differs from the value used to plan the update, then reconcile on the next run.

Create one standing `Capture inbox` issue. Create one weekly `Editorial desk — YYYY-Www` issue, keyed by ISO week in America/Los_Angeles, on the first Monday scan or first later run if Monday was missed. At bootstrap create the current week's desk immediately. Open at most three new story issues per weekly desk, not one per commit; when a prior story is still active, carry it instead of assigning another. Keep unsurfaced evidence-backed candidates locally and searchable through `status`/the desk selection process. Link new evidence to an existing story rather than repeatedly selling the same work.

Each story issue's agent-managed block contains: topic label (not a finished headline), intended reader, reader question/payoff, why now, cited evidence with verification status, three to five questions for Pedro, missing measurements/media, suggested original format, and a small distribution checklist. Include at least one credible secondary-pillar option when evidence supports it, but do not manufacture balance or let high-volume AI commits drown out a real machining milestone.

The weekly desk recommends one original at weekly cadence. At `twice-weekly`, permit two active originals but keep the absolute cap at two; channel derivatives do not become separate original quotas. At `paused`, continue collection and requested draft reviews but create no new weekly assignments or reminders. On two consecutive carried weeks, propose narrowing the same story or parking it, without adding new candidate assignments. A missed publication is not a debt. Compute consistency from recorded original-publication dates, excluding paused weeks; captures and merged drafts are not publications.

Every source scan is quiet unless it produces a substantive eligible PR review or a genuine blocker. There are no daily nudges: Pedro chose the weekly desk over daily check-ins. The static inbox and weekly assignment include a before-shop capture checklist so the system does not pretend it can recover missed footage. Do not infer a shop session from a CAD commit.

Use stable hidden markers for managed sections and actions, such as `<!-- eic:desk:2026-W39 -->`, `<!-- eic:story:<candidate-id> -->`, and `<!-- eic:review:<pr>:<head-sha>:<policy-hash> -->`. Preserve human issue text and comments outside managed blocks. Before a write, re-read the target and merge only the managed block; use a durable outbox and reconcile remote markers after uncertain delivery before retrying. Paginate lookup/recovery reads. Never delete issues or rewrite Pedro's prose. Leave a no-op run completely silent on GitHub.

Create explicit prerequisite issues for blog/publishing destination and analytics. Link the existing Harmonic Analyzer landing/email-capture issue #472 rather than duplicate its scope. These issues do not consume the weekly content quota. Until destinations exist, suggest only verified links such as the repository/logbook; never invent signup or Kickstarter prelaunch URLs.

Return located problems/questions and at most five high-impact actionable findings per round, with remaining issues grouped briefly. Grammar suggestions must reference an exact existing span, fit within one sentence, and be at most 12 words of replacement.
